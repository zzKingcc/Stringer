# 域（Domain）顶层模型设计

> 定位：这是 Stringer 最核心的抽象，其他一切能力都应挂在它上面
> 结论先行：**域必须从「工具可见性的派生标签」升级为「Agent 能力的装配与治理单元」**
> 与 `REDESIGN-PLAN.md` 的关系：那份文档里的 9 个主题，在本文的架构里**全部变成域的挂载项**；本文是那份规划的上层

---

## 0 一句话结论

现在的域是一个**派生标签**：由工具注解 `profiles` 反推出来、只有一个维度（哪些工具可见）、配置散落在四处。
它应该是**装配清单 + 治理单元**：由域自己声明「用哪些工具、哪个模型、哪个知识空间、哪份提示词、什么记忆策略、什么配额」，成为一次 AI 能力的**可发布、可灰度、可计量、可授权**的交付单位。

**并且要把方向反过来：不是工具声明自己属于哪个域，而是域引用它需要的工具与能力。**

---

## 1 诊断：现在的域是什么

### 1.1 三个根本错位

| # | 错位 | 具体表现 | 代码证据 |
| --- | --- | --- | --- |
| 1 | **派生而非声明** | 域不是被"创建"的，而是被工具"顺带声明"出来的；没有创建入口、没有 owner、没有描述、没有生命周期 | `ToolRegistry.register()` 里 `remember(descriptor.profiles())`；`knownProfiles = declaredProfiles ∪ 现存工具声明` |
| 2 | **单维而非装配** | 域只回答一个问题"哪些工具可见"。模型、提示词、知识库、记忆、配额、编排策略全是全局单例或硬编码 | 模型：`LlmModelHolder` 单端点；提示词：`profiles.json` 只有一段文本；知识库：全局一个索引 `stringer_knowledge`；记忆：`DualConstraintChatMemory` 50/30k 构造参数 |
| 3 | **方向反了** | 工具的归属写在**工具侧代码**里（`@StringerTool(profiles={"customer"})`），域无法决定自己需要什么；接一个新域要改工具代码并重启 | 注解上的 `profiles` 字段是可见性的唯一定义源 |

### 1.2 这个设计在扩张时会立刻撞墙的三个场景

1. **两个域要用同一个工具，但审批策略不同**：`refundOrder` 在客服域免审批、在财务域要双人审批 —— 现在做不到，审批模式写在工具的 `@ToolPolicy` 上，全局唯一。
2. **两个域要用不同的模型**：客服域用便宜的小模型、合同审查域用大模型 —— 现在做不到，`LlmModelHolder` 全局一个。
3. **两个域要用不同的知识库与检索策略**：售后域只查售后手册、法务域只查合同库 —— 现在做不到，索引名全局一个，检索权重全局一份。

这三件事是"域"这个抽象存在的**全部理由**。做不到，域就只是个过滤器。

### 1.3 一个补丁留下的线索

`declaredProfiles` 的设计（域一经声明永不移除、"域不存在"的判据是"是否被声明过"而不是"此刻有没有工具"）说明作者已经意识到域不该跟着工具死活。**但这是用补丁去模拟一个本该独立存在的实体** —— 如果域本身是一等公民，"域还活着吗"这个问题根本不会出现。

## 2 域应该是什么

### 2.1 定义

> **域 = 一个可独立发布、可灰度、可计量、可授权的 Agent 能力单元。**

它是业务的 AI 切片，而不是技术上的工具集合。判断标准：**一个域应当能完整回答"这次对话用什么、花多少、谁负责、怎么变"**。

### 2.2 十项装配清单（Domain Manifest）

| # | 装配项 | 内容 | 现状 |
| --- | --- | --- | --- |
| 1 | 身份 | `domainId`、名称、描述、命名空间、owner、标签 | 无（只有名字字符串） |
| 2 | 工具集 | 引用工具名或能力标签；**域级覆盖**：审批模式、超时、并发上限、配额 | 仅有可见性，覆盖能力为零 |
| 3 | 模型绑定 | chat / embedding / rerank 的**模型别名**引用 + 参数覆盖（temperature、maxTokens）+ 降级链 | 全局单端点 |
| 4 | 知识绑定 | 知识空间（索引/命名空间）、检索策略（top-n、权重、rerank 开关）、ACL 范围 | 全局一个索引 + 权重硬编码 |
| 5 | 提示词 | 基线引用 + 域差异（**版本化**，支持灰度与回滚） | 一段文本，无版本 |
| 6 | 记忆与上下文 | 窗口策略（条数 / token）、TTL、是否启用长期记忆与用户画像 | 50 / 30k 构造参数 |
| 7 | 编排策略 | 图形态（是否启用自检 / 子图）、最大工具轮次、单轮超时、并发上限 | 图结构编译期固定 |
| 8 | 治理 | 默认审批策略、敏感字段、脱敏规则、审计级别 | 仅审批，其余登记不生效 |
| 9 | 配额与预算 | token 预算、QPS、工具调用上限、超限行为（拒绝 / 降级 / 排队） | 无 |
| 10 | 生命周期 | 草稿 / 灰度 / 生效 / 弃用；版本与变更记录 | 无 |

**这十项每一项背后都是一个可替换的实现**（模型来源、检索器、记忆存储、审批判定器……），所以域的十条装配线，正好是 SPI 的十个落点 —— 这也回答了 `api.spi` 该怎么设计：**SPI 的服务对象是域，不是全局配置**。

### 2.3 双向声明、交集生效：谁的信息，谁定边界

先纠正 2.2 之后一个容易推过头的地方：**"方向反转"只适用于装配项，不适用于工具归属。**

| 关系 | 谁主导 | 为什么 |
| --- | --- | --- |
| **工具 → 域**（我能被谁用） | **工具侧强制声明** | 工具作者最清楚它适用于哪些场景、副作用多大 —— 这是**授权**，不是建议 |
| **域 → 工具**（我用谁、怎么用） | 域侧 | 域在工具的授权范围内决定用不用、是否加审批、超时与配额放多少 |
| **域 → 模型 / 提示词 / 知识 / 记忆 / 配额** | 域侧 | 这些信息工具侧根本不持有 |

**规则（四条，缺一不可）**

| # | 规则 | 说明 |
| --- | --- | --- |
| 1 | 工具**必须声明**可用域；**留空归入默认域 `default`** | `domains` 留空不再报错，而是归一化为 `{default}`（保守语义：只在默认域可用）。确需全域可用须**显式**写通配 `{"*"}`。每个留空的工具在启动期打 WARN，并在管控台计入「待分类工具」 |
| 2 | 域只能在授权范围内选择 | `tools: { include: ["order.*", "tag:crm"], exclude: [...] }`；工具声明是**必要条件**，域无法突破 |
| 3 | 生效条件＝**交集** | `域 ∈ 工具声明域` **且** `工具 ∈ 域引用集合` 才可被模型看到。任一侧未通过都不生效 |
| 4 | 越界即失败，不静默 | 域引用了未授权工具 → **发布期校验失败**（fail-closed，与"域不存在不降级成 10004"的风格一致）；运行时复核仍保留为兜底 |

**优先级**：工具声明边界 > 域 `exclude` > 域 `include`。域可以再收紧，不能放宽。

- 语义升级：注解字段从 `profiles` 更名为 `domains`（"可见性"→"授权边界"），`profiles` 保留为 deprecated 别名一个版本周期。
- **兼容**：现有已声明 `profiles` 的工具原样生效；留空的工具归入 `default`，行为从"全域可见"收紧为"只在默认域可见"，启动期告警提示补声明。
- 自动建域仍然保留：工具声明的域若尚未注册 → 自动创建影子域（带 `derived` 来源标记），零配置体验不变。

#### 2.3.1 默认域 `default`：兜底、种子与"待分类"桶

**服务启动时预置一个内置域 `default`**，它是整个模型的兜底与收敛点：

| 特性 | 规定 |
| --- | --- |
| 创建 | 启动期幂等 seed（`builtin` 来源标记），不需要人工建 |
| 保护 | **不可删除**（否则留空的工具与对话无处安放）；可编辑装配、可改名称与提示词 |
| 工具兜底 | 声明留空 → 归一化为 `{default}` |
| 对话兜底 | 请求未指定域（旧通道、裸 HTTP、脚本）→ 落到 `default`；SDK 绑定路径不受影响 |
| 装配初值 | `default` 的装配**由现有全局配置初始化**（全局模型、全局提示词、全局知识索引、全局记忆策略）—— 见下 |
| 用量归属 | 单独归集，可视作"未分类"桶 |
| 通配区别 | 留空＝只属于 `default`（保守）；`{"*"}`＝任何域可用（显式全域）。两者语义不同，不可混用 |

**这个决定顺手消掉了一层结构**：原来"全局配置 + 域配置"是两层，现在**全局配置＝`default` 域的装配，yaml 与落盘 JSON 只作为它的初始化种子（bootstrap）**。于是「域未声明就回落全局」这句话，精确化为「其他域未声明时继承 `default` 的对应装配项」—— 规则只剩一条继承链，没有第二套机制。

**兜底域由使用方自行治理**：平台只做**事实呈现**（`default` 域下的工具清单、调用计数），**不设健康阈值、不做告警策略** —— 用多少、要不要清空、清到什么程度，由使用方自己决定。平台的责任是把事实摆出来，而不是规定"它应该趋近于 0"。

### 2.4 派生 vs 主导：为什么必须域主导

**判据一句话：绑定关系的信息在哪一侧，权威就该在哪一侧。**

域要绑的十项里，模型、提示词、知识空间、记忆策略、配额、编排策略、版本、owner、调用方这**九项的信息只存在于域这一侧** —— 工具既不知道也不该关心"谁会调我、用哪个模型调我"。工具侧能提供的是**授权声明**（我允许被哪些域使用），域侧能提供的是**装配与选择**（我用谁、怎么用）—— 两者维度不同，**取交集**，而不是用一方取代另一方。

| # | 维度 | 域被派生（工具声明域） | 域主导（域引用能力） |
| --- | --- | --- | --- |
| 1 | 表达能力 | 只能表达「工具 → 域」一条边；模型、提示词、配额无从表达（工具没有这些信息） | 十条绑定边都能表达 |
| 2 | 变更主体 | 改域要动**工具代码**（工具由业务开发维护、要走发版） | 改域是**运行时配置**（域由 AI 运营者维护、随时可改） |
| 3 | 多 LLM 场景 | **直接不成立**：同一工具被多个域使用、各用不同模型，而模型不是工具的属性 | 天然成立：模型别名由域绑定 |
| 4 | 变更成本（N:M） | 新增一个域要改**所有**相关工具：O(工具数) | 新增域只改一处：O(1) |
| 5 | 治理承载 | 派生出来的东西无法承载 owner / 版本 / 配额 / 授权 | 域是实体，天然承载 |

**依赖方向的原则**：稳定的东西（工具实现）不应该依赖多变的编排策略（域配置）。工具声明域，等于让稳定者依赖多变者 —— 方向错了。

**但"派生"不是错误，是阶段匹配。** v1 的定位是「工具治理」，域只是工具分组，派生模型用零配置换来了极低的接入成本 —— 在单团队、单场景、工具与域一一对应的形态下这是最优解。一旦走向「多 LLM + 多场景 + 多租户」，派生立刻变成瓶颈。**问题不在当初做错了，而在于定位扩张后模型必须升级。**

**共存规则：不需要二选一**

| 规则 | 说明 |
| --- | --- |
| 权威方向（工具归属） | **工具侧强制声明可用域**：留空 → 归入内置域 `default`；全域可用须显式写 `{"*"}`；留空会在启动期告警并计入「待分类工具」 |
| 权威方向（装配项） | **域侧主导**：模型、提示词、知识、记忆、配额只能由域绑定 |
| 生效条件 | **交集**：`域 ∈ 工具声明域` 且 `工具 ∈ 域引用集合` |
| 自动建域 | 工具声明了尚未注册的域 → 自动创建影子域（`derived` 来源标记） |
| 冲突优先级 | 工具声明边界 > 域 `exclude` > 域 `include`；域只能收紧，不能放宽 |
| 越界处理 | 域引用未授权工具 → 发布期校验失败（fail-closed），不静默剔除 |

### 2.5 多 LLM 接入：域绑定的落地形态

多 LLM 不是"在域里存一个模型地址"，而是三层：

| 层 | 内容 | 为什么这样分 |
| --- | --- | --- |
| **模型档案**（Model Profile） | 一个别名 → {端点, Key 引用, 模型名, 参数, 降级链}，如 `fast` / `smart` / `local` / `emb-bge` | 端点会变、Key 会换、供应商会换，域不该硬编码这些 |
| **域内角色绑定** | 域按**用途**绑别名：`chat`（主对话）、`planner`（任务拆解）、`summarizer`（压缩历史）、`embedding`、`rerank` | 同一域内不同步骤可用不同模型；这是域内策略，工具无从知晓 |
| **调用期解析** | 运行时按「域 → 角色 → 别名 → 端点」解析，带降级与熔断 | 解析结果可缓存，Key 轮换与端点切换对域透明 |

提示词同理：**模板注册表**（模板 + 变量 + 版本）→ 域绑定模板并填变量（品牌话术、业务术语），而不是在域里存一整段裸文本。这样同一模板可在多域复用、改一处生效多处，且能灰度。

**一句话原则：域绑定的是「引用」，不是「值」** —— 绑别名而不是端点，绑模板而不是文本，绑知识空间而不是索引名。这一条决定了"换模型 / 换供应商 / 换索引"要不要动域。

### 2.6 三个关系维度

| 关系 | 含义 | 作用 |
| --- | --- | --- |
| **域 × 租户** = 域实例 | 租户使用某域时产生实例：继承域配置，覆盖租户特有项（模型 Key、配额、知识分区、提示词微调） | 一套域定义服务多租户，避免"每租户复制一份配置" |
| **域 × 版本** = 域发布 | 域有版本：`draft → canary → active → deprecated`，可回滚 | 提示词/模型/工具集变更成为可灰度的发布动作 |
| **域 × 调用方** = 域凭证 | 哪个应用可以调哪个域；用量记在调用方头上 | 配额与成本可归属；也是域从"命名空间"变成"治理边界"的前提 |

#### 2.6.1 澄清：域 ≠ 租户

域升级为治理单元后，最容易产生的误解是"域就变成租户了"。**两者是正交的两个维度。**

| | 域（Domain） | 租户（Tenant） |
| --- | --- | --- |
| 回答的问题 | **用什么**：哪些工具、哪个模型、哪份提示词与知识、什么策略 | **谁的**：谁的数据、谁的额度、谁的账单 |
| 定义者 | 能力提供方（产品 / 算法 / AI 运营） | 客户 / 业务线 |
| 生命周期 | 草稿 → 灰度 → 发布 → 弃用，带版本 | 开通 → 配额 → 停用，带账期 |
| 隔离含义 | **逻辑边界**：可见性与配置 | **数据边界**：key 前缀、索引 filter，必要时物理隔离 |
| 冲突形态 | 装配冲突（同一工具在两个域审批策略不同） | 越界（A 读到 B 的知识与会话） |
| 数量级 | 数十（一个场景一个域） | 数百到数千（一个客户一个租户） |

**一条实用判据：**

> 两个"域"之间**需要不同的数据可见性** → 那是**租户**边界；
> 两个"域"只是**用不同工具 / 模型 / 提示词**，数据可以共享 → 那是**域**边界。

**所以：域主导让平台"具备了承载多租户的挂载点"，但不等于变成多租户。** 多租户还要额外补三件事，而这些域带不来：存储层的 tenant 维度、凭证与密钥隔离、配额仲裁与计费。

**把域当租户用（一个客户一对域）会产生三种债：**

1. **域数量爆炸** —— 域是按"数十"设计的概念，被当"数千"量级用；
2. **语义耦合** —— 无法表达"同一能力开放给多个客户"，每开一个客户就要复制一份域配置；
3. **归属混乱** —— 配额与成本记在域上，而不是记在客户头上，账单对不上。

**但要分清两条线：数据隔离是必经的，配置覆盖是可选的。**

| 线 | 内容 | 是否每个租户都需要 |
| --- | --- | --- |
| **数据面（必做）** | 会话、记忆、检查点、知识分区全部带 `tenant` 维度；配额与成本按 `(域, 租户)` 归集 | **是**。只要有多租户，这条线就必须有 |
| **控制面（默认共享）** | 工具集、编排策略、模型别名绑定、提示词模板、检索策略 —— 全租户共用一份域定义 | 否，默认共享 |
| **覆盖层（稀疏、可选）** | 仅当某租户需要**不同的值**时才生成：自带模型 Key（BYOK）、独立配额、话术变量微调 | 否。**只对有差异的租户生成** |

**同域多租户是主路径**：多个租户绑同一个域、共享同一套能力装配，只在数据面按租户切开。这时：

- 域是**模板**，不需要给每个租户复制一份配置；
- 调用期解析链路是 `域默认配置 → 租户覆盖（若存在）→ 生效配置`，没有覆盖的租户直接走域默认，零额外成本；
- 换句话说，**域实例不是"每租户一个"，而是"有覆盖的租户才有一个"** —— 它是稀疏的、按需创建的，不是必备品。

**三层判定（什么时候拆域、什么时候加租户、什么时候才用覆盖）：**

| 差异的性质 | 正确做法 | 反例 |
| --- | --- | --- |
| **能力装配不同**（工具集、模型档位、编排策略、是否审批） | **拆成两个域** | ❌ 在一个域里塞租户分支，配置爆炸且无法维护 |
| **数据与额度不同**（互不可见的会话与知识、各自账单） | **同域 + 租户维度** | ❌ 每客户复制一份域 |
| **同能力下的轻微差异**（自带 Key、配额档位、话术变量） | **租户覆盖层**（稀疏） | ❌ 差异化到影响装配，那又回到拆域 |

一句话：**数据不同 → 加租户；能力不同 → 拆域；值不同（且不影响装配） → 覆盖。** 覆盖层要克制，一旦某租户的覆盖多到"装配都不一样了"，说明它本该是另一个域。

### 2.7 入口形态

| 层 | 形态 | 说明 |
| --- | --- | --- |
| HTTP | `POST /api/v1/domains/{domainId}/chat` | 域成为 URL 资源；旧 `POST /api/agent/chat` + `profile` 保留为兼容入口 |
| 契约 | `AgentRequest.domainId`（`profile` 作为别名保留） | 核心字段从"自由文本"变成"受校验的资源标识" |
| SDK | ① 注解式：controller 上 `@DomainBinding("customer-service")`；② 注入式：`agentService.forDomain("customer-service")` 返回绑定域的 facade | 业务方不需要每次手写域字符串，域绑定成为**接线动作**而非参数传递 |
| 管控台 | 域空间从"只读视图"升级为**主编辑界面**：装配十项、看引用关系、发布灰度、看用量成本 | 现在是"域空间页 + 提示词页"两个只读视图拼事实 |

#### 2.7.1 调用侧：必须绑定域，且由 SDK 强制

域不能被"顺手传一个字符串"绕过。约束分三层，缺一层就有绕过的缝：

| 层 | 强制手段 | 效果 |
| --- | --- | --- |
| **编译期** | SDK 不提供"不带域"的调用形式：`DomainAgent agent = agentService.forDomain("customer-service")` 返回绑定域的 facade，其 `chat(...)` 签名里**没有** profile 参数；注解式 `@DomainBinding("customer-service")` 标在 Controller 上，注入的就是绑定后的 facade | 写不出"忘记传域"的代码 |
| **启动期** | 应用启动时向服务端校验：声明的域**必须存在**，否则中断启动（复用现有连通性探测的 fail-fast 机制，与"服务端必须先启动"同一哲学） | 配错域名不会等到线上第一次调用才暴露 |
| **运行期** | 服务端仍复核：缺域 `10009`、域不存在 `10004`（**不降级为全量工具**） | 客户端绕过了，服务端还兜着 |

配套的 HTTP 形态：`POST /api/v1/domains/{domainId}/chat` —— 路径里没有域，路由根本不存在，比"参数缺失"更硬。

**保留的兼容通道**：`AgentService.chat(AgentRequest)` 与 `POST /api/agent/chat` + `profile` 继续可用，但标记为 deprecated，文档明确它是**兜底通道**，新接入一律走绑定形态。

**一处注意**：注解式绑定要支持方法级覆盖类级（一个 Controller 里挂多个域的场景），否则用注入式。

## 3 域如何挂载其他能力

这是"最高层"的真正含义：**先把域立住，其他主题自动收敛成域的挂载项**。

| 上一轮的主题 | 在域模型下的位置 | 变化 |
| --- | --- | --- |
| T1 状态外置 | 域注册表是**第一个必须外置的状态** | 域被所有副本读取，天生要放 Redis/PG；顺带把工具注册表一起搬走 |
| T2 多租户 | 变成「域实例」的覆盖层 | 不再需要独立的"租户配置"概念 |
| T3 扩展点 SPI | 每个 SPI 服务**域的某项装配** | SPI 设计有了明确的服务对象，不再是无主接口 |
| T4 模型网关 | 模型网关是域「模型绑定」的**实现机制** | 路由/降级/熔断按域生效；提示词灰度变成域版本灰度的一部分 |
| T5 检索深化 | 检索是域「知识绑定」的实现 | 索引、权重、rerank 开关、ACL 全部按域配置 |
| T6 编排升级 | 编排策略是域的装配项之一 | 多 Agent 的入口：一个域可声明多个角色与子图 |
| T7 工具生态 | 工具治理是「工具集 + 域级覆盖」 | 版本灰度天然按域发布；MCP 工具只是另一种工具来源 |
| T8 契约演进 | `domainId` 是核心契约字段 | 契约版本化围绕域展开（域版本 + 协议版本） |
| T9 可观测 | 域是**天然的聚合维度** | 指标与成本按域归集，比按 sessionId 更有业务意义 |

## 4 生命周期与治理

| 能力 | 说明 |
| --- | --- |
| 引用完整性校验 | 域发布前检查：引用的工具是否存在、模型别名是否已配置且连通、知识空间是否可用、提示词版本是否存在 |
| 变更影响分析 | 改一个域影响哪些调用方、哪些租户；反向：下线一个工具会影响哪些域（现在是"域跟着消失"的隐式后果） |
| 发布与灰度 | 域版本支持权重灰度（10% 流量走新版本），异常自动回滚；回滚是"切版本"而不是"改配置" |
| Domain Pack | 域可导出/导入（含提示词、工具引用、检索策略），支持测试环境配置一键迁到生产 |
| 弃用流程 | `deprecated` 状态 + 调用方告警 + 宽限期，替代现在"工具一断域就没了"的隐式行为 |

## 5 一个必须做的架构取舍：域的信任模型

现在域是**调用方自行声明、平台无条件信任**的（源码注释明确写了"不是安全边界"）。这个取舍在"域只是一个过滤器"时是合理的。

**但一旦域承载配额、成本与授权，这个前提就不成立了**：调用方随便填一个域名字符串，就能用别人的配额、读别人的知识空间。

所以有一个必须做的二选一：

| 选项 | 含义 | 代价 |
| --- | --- | --- |
| **A：域降级为纯标签** | 域不承载配额与授权，只做工具集与提示词的组装 | 失去多租户计量、成本归属能力，域永远只是过滤器 |
| **B：域升级为治理边界** | 域与调用方绑定（注册的 clientId + 域授权关系），域身份可信 | 需要一个域授权模型与申请流程，接入成本上升 |

**我的判断：选 B，但分两步**。第一步（阶段 A）域先承载**非对抗性治理**（配额、成本、灰度）——这些场景即使被绕过也不致命；第二步等真有对外多租户时，再补域授权的强校验。这样既拿到治理能力，又不让接入成本一次跳高。

## 6 迁移路径（四步，每步都不破坏兼容）

| 步骤 | 动作 | 兼容策略 | 验收 |
| --- | --- | --- | --- |
| **S1 域注册表** | 新增 `DomainRegistry` 作为权威；域有了创建入口与元数据（名称/描述/owner/状态） | 现有从注解派生的域自动生成"影子域"（`legacy` 标记）；`knownProfiles` 语义保留，行为不变 | 管控台能看到域的元数据；现有 example 不改一行照跑 |
| **S2 装配项接管** | 模型、提示词、知识、记忆四项从全局配置迁入域；全局配置降级为"域未声明时的默认值" | 全局值作为兜底 fallback；单域部署下行为与现在一致 | 两个域配不同模型与知识空间，实测互不影响 |
| **S3 引用关系反转** | 工具侧保留 tags，域侧声明 include/exclude；域级覆盖审批、超时、配额 | 工具注解 `profiles` 转为 legacy 引用关系，继续生效 | 同一工具在两个域有不同审批策略，实测生效 |
| **S4 版本与灰度** | 域版本、灰度、回滚、Domain Pack 导入导出 | 无版本域视为 `v1` | 域改提示词后 10% 灰度，异常一键回滚 |

**顺序不能反**：S2 依赖 S1 的域注册表，S3 依赖 S2 的域配置承载能力。

## 7 待你拍板的问题

| # | 问题 | 选项 | 我的建议 |
| --- | --- | --- | --- |
| 1 | 域与工具的关系 | 继续工具声明域 / 反转成域引用工具 | **已论证（见 2.4）：反转**，工具侧保留 `suggestedProfiles` 作建议、影子域作初始配置，legacy 兼容两个版本周期 |
| 2 | 域的信任模型 | A 纯标签 / B 治理边界 | **B 分两步走**（见第 5 节） |
| 3 | 域 × 租户 | 不做（域即租户）/ 做域实例与覆盖 | 短期**不做**（先单租户把域做扎实），但 key 与索引名保留注入点 |
| 4 | 域的颗粒度 | 粗（一个业务线一个域）/ 细（一个场景一个域） | **一个场景一个域**，用 namespace 与标签做分组；域太多是不可逆的治理债 |
| 5 | 域配置的存放 | 管控台落盘 JSON（现状）/ 文件化 Manifest（可进 Git） | **文件化 Manifest 为主 + 管控台编辑为辅**，让域配置可评审、可 diff、可回滚 |
| 6 | 是否要 URL 资源化 | 只改契约字段 / 同时开 `/api/v1/domains/{id}/chat` | **同时开**，REST 语义更清晰，也让网关层能按域做路由与限流 |
